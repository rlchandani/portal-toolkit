Tier 1 — New Power Tools

Highest user value

Capabilities users of a Portal management tool expect but the app doesn't have yet. All four are new ADB channels over the connection the app already holds — moderate effort, big payoff.

1Remote Shell (Terminal)

An interactive terminal into the Portal. Power users constantly need one-off commands — pm list packages, settings put, am start — and today they must fall back to a PC. A command history, quick-command chips (reboot, list packages, wm size), and copyable output make this the single most-requested class of feature in device-toolkit apps.

Impact: Very HighEffort: Smalldadb.shell() — already used internally
How: the app already runs shell commands everywhere (e.g. PortalConnectionManager.getDeviceStatus). This just exposes the same channel as a UI: a LazyColumn transcript + TextField + persisted history. Guard destructive commands with a confirm dialog.

2Live Logcat Viewer

Stream the Portal's logs to the phone with level filters, package filter, pause, and share-as-file. Essential for the app's core audience: people sideloading apps onto a discontinued device and needing to see why an install or launch failed. Pairs perfectly with the existing install flow — “Install failed → View logs”.

Impact: HighEffort: Mediumshell "logcat" streaming via dadb open()
How: open a long-lived shell:logcat -v brief stream, parse lines into a bounded ring buffer (e.g. 2,000 lines) to keep memory flat, render with a lazy list. Filters are client-side; “errors only” chip maps to logcat *:E.

3Two-Way File Manager

Browse the Portal's storage, pull files back to the phone, push any file (not just photos), delete, and see sizes. Today the data flow is one-way — photos go up, nothing comes back. A file manager subsumes photo upload, enables pulling media/backups off the device before a reset, and makes the Portal feel like a normal managed device.

Impact: HighEffort: Mediumls -la parsing + dadb push/pull (sync protocol)
How: dadb.pull()/push() already exist and are used by backup. Directory listing via shell:ls -la parsed into rows; breadcrumb stack for navigation; long-press for multi-select. Restrict writes outside /sdcard behind an “advanced” toggle.

4Screen Capture & Live Peek

See what's on the Portal's display without walking over to it. One-tap screenshot (saved to the phone), plus a “live peek” mode that refreshes every 1–2 seconds — enough to verify an app launched, navigate a setup wizard remotely, or confirm the device isn't stuck on a boot screen. Full scrcpy-style mirroring is out of scope; polling screenshots gets 90% of the value at 5% of the complexity.

Impact: HighEffort: Small–Mediumshell "screencap -p" → pull → Bitmap
How: screencap -p /sdcard/.pt_peek.png then dadb.pull(), decode, display. Live peek = loop with a coroutine; tap-to-input later via input tap x y mapped from image coordinates (stretch goal).

11Screensaver Manager ★ Requested

A dedicated manager for the folder the Portal's screensaver / photo-frame app reads from. Today the Photos tab is upload-only and one-way: it pushes to a hardcoded /sdcard/Pictures/PortalInstaller and you can never see what's already on the device. This replaces it with a full round-trip photo manager:

  • Choose the screensaver folder — pick any folder on the Portal (with smart suggestions: the app scans for known screensaver dirs and folders full of images), remembered per saved device.
  • See what's already there — thumbnail grid of the device's current contents, with size and date. Thumbnails are generated on-device (screencap-free: pull a downscaled copy) and cached on the phone.
  • Manage in place — multi-select to delete, move/copy to another folder, or pull back to the phone. Rename supported.
  • Smart upload — when adding photos, duplicates already on the device are flagged and skipped by default; a storage meter shows the folder's footprint before you commit.
Impact: Very High — core photo-frame use caseEffort: Mediumls/stat parsing + dadb push/pull + mv/rm/cp
How: builds directly on the File Manager plumbing (#3) — same ls -la parser and dadb push/pull, specialized into a photo-first UI. Folder choice stored per device in SavedPortalStore. Dedupe via file size + name (fast) with optional md5 (md5sum exists on the Portal). Thumbnails: pull each image once at full size on Wi-Fi, downscale with BitmapFactory.inSampleSize, cache keyed by path+mtime. The existing Photos tab becomes this screen — no separate upload flow to maintain.

Tier 2 — Polish Existing Flows

Reliability & UX

The features exist but feel rough. These upgrades make the current app feel finished and trustworthy.

5Device Dashboard + Power Controls

Promote the buried device-status text into a proper dashboard: storage / RAM gauges, uptime, battery-less health at a glance — plus the controls that are conspicuously missing today: Reboot, Reboot to recovery, Screen off/on, and Launch app. Today there is no way to reboot a Portal from the app at all.

Impact: HighEffort: Smallreboot / input keyevent / monkey -p pkg 1
How: data already collected by getDeviceStatus() (df, meminfo, getprop) — just render it. Controls are one-liners: shell:reboot, input keyevent KEYCODE_SLEEP, monkey -p pkg -c android.intent.category.LAUNCHER 1. Confirm dialogs on reboot.

6Rich Portal App List

The Portal apps list currently shows raw package names with no icons (the icon path is fetched but never used). Upgrade it: real app labels, icons pulled from the APK, and per-app actions — Launch, Force stop, Clear data, in addition to Uninstall. This turns a read-only list into an app manager.

Impact: Medium–HighEffort: Mediumpull base.apk → PackageManager.getPackageArchiveInfo
How: iconApkPath is already plumbed but always null (PortalConnectionManager.kt:400). Pull each base.apk header once, extract label + icon with the phone's own PackageManager, cache to disk keyed by package+version.

7Connection Health & Auto-Reconnect

Today a dropped Wi-Fi connection is invisible until the next operation fails with a confusing error. Add a lightweight heartbeat (a no-op shell echo every ~20s), a persistent status chip in the app bar on every screen, and automatic reconnect with backoff when the link drops — with a toast so the user knows what happened.

Impact: High (trust)Effort: Smallheartbeat coroutine + reconnect w/ backoff
How: a while(isActive) loop in the ViewModel issuing shell:echo ok; on failure flip ConnectionState to Reconnecting and retry the saved host with exponential backoff (2s → 30s). The status chip shown in every mock above is this feature.

8Real Progress + Cancel Everywhere

Installs currently show only an elapsed-seconds ticker; photo uploads report only the last error; backups, restores, scans and profile installs can't be cancelled at all. Add byte-level progress (the app controls the stream when pushing files), per-item results for batch operations, and a Cancel button on every long-running job.

Impact: High (trust)Effort: Mediumcounting Source wrapper + cancellable coroutine Jobs
How: wrap the okio Source in a counting decorator to emit bytes-sent; keep each operation's Job so Cancel actually cancels; change batch states to carry per-item results (e.g. ProfileApplyState.Done(succeeded, failed) — today it reports Success even with failures).

9Dark Theme + Dynamic Color

The color scheme is a single hardcoded light palette in MainActivity.kt. Add a proper ui/theme package with a dark scheme (teal survives beautifully in dark mode), follow-system by default, and optional Material You dynamic color on Android 12+ phones. A device-management tool gets used in the evening on the couch — dark mode is table stakes.

Impact: MediumEffort: SmalldarkColorScheme() + isSystemInDarkTheme()
How: extract the palette into ui/theme/Theme.kt, add darkColorScheme(primary = 0xFF4FD8D4, background = 0xFF131615…), a 3-way setting (System/Light/Dark) in the existing Settings tab, and dynamicDarkColorScheme() when available.

Tier 3 — Foundation Work

Enables everything above

Invisible to users but pays for itself before Tier 1 ships — the new Tools tab shouldn't be bolted onto a 3,659-line file.

10Architecture Cleanup

10aSplit MainScreen.kt (3,659 lines → ~12 focused files) into ui/devices/, ui/apps/, ui/photos/, ui/tools/, ui/theme/. Purely mechanical, zero behavior change, do it first.
10bAdopt Navigation-Compose — replaces the raw selectedTab` int, gives back-stack, deep links, and preserved sub-tab state.
10cRemove reflection into dadb internals (discovery + USB bridge both reflect into private APIs with a "re-test after every version bump" comment). Upstream a PR to dadb or vendor the two functions — this is a silent-breakage time bomb.
10dSplit the god-ViewModel per feature area, move history persistence out of the UI layer (it writes SharedPreferences directly), migrate prefs to DataStore.
10eAdd tests — there are currently zero. Start with the pure logic: backup manifest validation, zip-slip protection, ls/logcat parsers, minSdk gate.
10fDelete dead code — WirelessAdbTab is defined but never called; update Compose BOM (2023.10) and compileSdk 34 → 35.
